## What this key does

It signs the zopen community's artefacts: 161 RPM packages under
`https://repo.zopen.community/pulp/content/zopen/`, plus pax bundles produced
by `zopen-build --sign-pax`. Consumers see it through `dnf`:

```
[zopen]
baseurl=https://repo.zopen.community/pulp/content/zopen/
gpgkey=https://repo.zopen.community/pulp/content/keys/zopen.pub
gpgcheck=1
```

`gpgcheck=1` means a signature failure stops the install. That is the entire
enforcement story for the zopen repository.

## Why it needs an attestation

The key is **self-signed only**: the only certifications on it are its own.
There is no third-party signature, no fingerprint published on zopen.community,
and no independent channel for the fingerprint at all — the sole binding
between the key and the project is TLS to `repo.zopen.community`, which is the
same host that serves the packages.

So today a consumer has one question with no answer: *is this the real zopen
key, or one substituted by a mirror or a network position?* A signature by a
WG member who compared the fingerprint out-of-band answers it.

Note the chain precisely: an RPM's signature verifies against this key, and
this key is attested by the WG members named above. ZTRUST says nothing about
the RPMs themselves.

## Completing this attestation

Two WG members, one of whom must have confirmed the fingerprint with a zopen
maintainer through a channel other than the repository itself:

```sh
# 1. Fetch and prove the bytes
curl -O https://repo.zopen.community/pulp/content/keys/zopen.pub
curl -O https://repo.zopen.community/pulp/content/keys/PULP_MANIFEST
sha256sum zopen.pub     # must equal the SHA-256 recorded above

# 2. Confirm the fingerprint, out loud, with the maintainer
gpg --show-keys zopen.pub
#   C1A01D8A 583E1A6A 72BF8AC0 6EBA6049 2F343463

# 3. Sign at an honest level and export the signed copy
gpg --ask-cert-level --sign-key 6EBA60492F343463
gpg --armor --export 6EBA60492F343463 \
  > pgp/projects/0x6eba60492f343463-zosopentoolsmain@gmail.com-signing.asc

# 4. Record it
#    - change Status to "signed", fill in Verified by / Date / Cert level
#    - append the armored block to pgp/pgp-bundle.asc so the signed copy is
#      what consumers receive
```

Then ask the zopen maintainers to publish the full fingerprint in
`zopen.community/Guides/RpmPackages` and to link back to this file, so the
attestation is reachable from the place consumers actually install from. Until
that link exists, this file is useful only to people who already know to look
for it.

## Rotation

The key expires **2027-10-21**. Before then the zopen project needs to publish
a successor, overlap the two keys for at least one release cycle, and state how
consumers re-import. When that happens:

1. Add an attestation for the new key.
2. Mark this file `revoked` or `superseded` with the successor's fingerprint.
3. Keep the old key published: signatures made with it must remain verifiable.
4. Watch the upstream `PULP_MANIFEST`; the sha256 changes when the key is
   replaced, and that is the prompt to start this process.

## Risk notes for the working group

These belong in the collection's advisory material, not in the attestation:

- One key signs every package in the repository. Compromise or loss means
  re-signing the entire catalogue and every consumer re-importing.
- The UID is a shared gmail mailbox with no organisational binding.
- `PULP_MANIFEST` is an unsigned checksum list served from the same host as the
  key, so it detects mirror corruption but not key substitution.
- There is no published revocation path.
